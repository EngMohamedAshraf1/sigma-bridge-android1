# Private Chat Technical Documentation

## Scope

This document describes the current Private Chat implementation only. Telegram is a separate subsystem and is outside the scope of Private Chat maintenance unless a task explicitly names Telegram.

## Product goal

The MVP is a simple private conversation between two Sigma Bridge users. The current product flow is:

```text
Google Login
   -> Private Chats
      -> create/find a contact by Sigma Bridge identity
         -> open 1-to-1 chat
            -> send/receive messages
               -> automatic translation
                  -> Delivered / Read receipts
```

The default MVP translation pair is Russian -> Arabic, while the language catalog already contains additional languages and Auto-detect. `LanguagePair.DEFAULT_MVP_PAIR` is currently Russian as source and Arabic as target.

## Authentication

`ChatAccountRepository` is the application boundary for Private Chat authentication. It uses Supabase Auth and signs users in with a Google ID token. Google is the only configured provider in the current implementation.

Legacy anonymous-auth sessions are deliberately not treated as authenticated Private Chat accounts. `isAuthenticated()` checks whether the current Supabase user has an email.

`GoogleSignInManager` uses AndroidX Credential Manager plus Google ID. It creates a cryptographically random nonce, hashes it for the Google request, and returns the ID token together with the raw nonce. The Supabase Auth layer receives the token and nonce for sign-in validation.

## Persistent identity

`ChatIdentity` is a singleton backed by application `SharedPreferences` named `sigma_bridge_chat_identity`.

Stored values include:

- `my_id`: the user-facing Sigma Bridge ID.
- `partner_id`: the currently selected partner for foreground UI compatibility.
- `device_public_id`: a stable identifier for the Android installation.

The user-facing ID has the format `SB-...` and is generated from secure random bytes. It is intentionally persisted so it normally survives app restarts.

The device identifier is separate because a user identity and a physical/app installation are different concepts.

### Identity recovery

During device registration, Supabase may return `PUBLIC_ID_ALREADY_IN_USE`. The implementation handles this specific case by generating a fresh public ID and retrying registration once.

This is a recovery mechanism, not normal behavior. Code must never regenerate the user's ID merely because a conversation failed, the network changed, or the app was reopened.

## Conversation identity

The client derives conversation identity from the two participant public IDs.

### Topic

`conversationTopicFor(partnerId)` sorts the two IDs, joins them with `|`, hashes the result with SHA-256, and uses the first 32 hexadecimal characters in:

```text
sigma-bridge-<hash-prefix>
```

Sorting makes the topic symmetric: A+B produces the same value as B+A.

### Conversation key

`conversationKeyFor(partnerId)` computes the SHA-256 digest of the same sorted identity pair. This is the 256-bit key input used by the current AES-GCM chat encryption implementation.

### Fingerprint

`securityFingerprint()` derives a compact numeric fingerprint from a further SHA-256 digest of the conversation key. It is intended as a human-visible identifier for the current conversation security context, not as a secret.

## Cryptography

`ChatCrypto` implements the current message encryption protocol.

The payload format is versioned with the `sb2:` prefix. The encrypted payload contains a version byte, a random 12-byte initialization vector, ciphertext, and a 128-bit GCM authentication tag. Base64 URL-safe encoding without padding is used for transport.

Two styles of decryption exist:

- `decrypt(...)` uses the currently selected partner/conversation.
- `decryptForPartner(..., partnerId)` derives the key for an explicit partner without mutating the currently selected partner.

The second form is important to background processing because a background message must not depend on whatever conversation the UI happens to have open.

### Security boundary

The current design is encrypted transport/persistence based on deterministic conversation keys derived from participant IDs. It is **not** a Signal-style ratcheting protocol and should not be documented as one. There is currently no documented asymmetric session-key exchange, forward-secret ratchet, or per-device public-key protocol for message encryption.

## Data model

The chat domain intentionally distinguishes transport, delivery state, and translation state.

### Message

`ChatMessage` contains:

```text
id
senderId
text
createdAt
deliveryStatus
originalText
translatedText
translationStatus
```

The UUID in `id` is generated by the local device for an outgoing message and is sent to Supabase as `client_message_id`.

### Delivery status

```text
PENDING
SENT
DELIVERED
READ
```

Statuses are monotonic. A receipt is an upgrade, not a replacement with an older state.

### Translation status

```text
PENDING
COMPLETED
FAILED
```

Translation state is deliberately independent from delivery state.

## Outgoing message lifecycle

When the user presses Send:

1. The text is trimmed and empty messages are ignored.
2. A new UUID is generated locally.
3. A `ChatMessage` is created with `PENDING` delivery state.
4. The message is immediately added to the visible list.
5. The message is written to `ChatHistoryStore`.
6. The message is written to `ChatOutboxStore`.
7. A conversation preview is updated.
8. Delivery is attempted asynchronously.

The Supabase repository then:

1. Validates that the supplied topic is the active identity topic.
2. Ensures the current device/conversation is registered.
3. Encrypts the message text.
4. Calls `sigma_send_message` with the conversation key, local client UUID, sender device ID, ciphertext, nonce, and message version.
5. On success, the outbox item is removed.
6. Local state changes from `PENDING` to `SENT`.

If delivery fails, the item remains in the outbox and background retry logic can attempt it again.

## Incoming message lifecycle

The foreground `ChatViewModel` listens to `ChatEvent.Message`.

The critical behavior is that transport and translation are separate:

```text
Remote message arrives
        |
        v
Decrypt
        |
        v
Create original ChatMessage
        |
        +--> immediately add to UI
        +--> immediately save to history
        +--> immediately send Read receipt
        |
        v
Start translation coroutine
        |
   +----+----+
   |         |
 success   failure
   |         |
   v         v
show       keep original
translated text
```

The message is never allowed to disappear merely because the translation service is slow or unavailable.

### Successful translation

`translatedText` is populated, `text` becomes the translated text, and the status becomes `COMPLETED`.

### Failed translation

`translatedText` remains null, `text` stays equal to `originalText`, and the status becomes `FAILED`. The user can therefore still read the actual received message.

### Conversation switching during translation

Translation updates are guarded by the conversation `historyKey`. The background translation coroutine updates persistent history regardless of which chat is open, but it only updates the currently visible `_messages` when the original conversation is still active.

This prevents a late translation response from appearing inside another open conversation.

## Read receipts

Read is triggered independently from translation.

When an incoming message becomes visible, `sendReadReceiptForMessage(...)` sends a `ChatReceipt` with the message ID and type `READ`. Duplicate sends are suppressed with `readReceiptSentIds`.

`markVisibleMessagesRead()` can also mark all currently displayed incoming IDs as read. The unread store is cleared for that conversation when visible messages are marked read.

## Receipt persistence

The Supabase RPC `sigma_set_receipt` receives the authoritative server message UUID, not the local client UUID. The current documented baseline resolves the server message through the current conversation plus `client_message_id` and then calls the RPC.

The current baseline intentionally does not include the later experimental change that removed the conversation lookup from `setReceipt()`.

This distinction is important when debugging historical branches: do not assume that every newer experimental receipt implementation is part of the current release baseline.

## Receipt polling

The current foreground Supabase repository polls `message_receipts` every second. It resolves each receipt's `message_id` back to the message row in the active conversation, obtains `client_message_id`, and emits either `ChatEvent.Read` or `ChatEvent.Delivered`.

The syntax of `fetchReceipts()` was explicitly corrected in the `6bb07de`-based release line. The current version uses a straightforward `if/else if` branch for `readAt` versus `deliveredAt`.

## Local history

`ChatHistoryStore` stores serialized `ChatMessage` objects in `SharedPreferences` named `sigma_bridge_chat_history`.

The preference key is based on SHA-256 of the conversation key, so the local storage namespace is tied to the participant pair rather than to the current UI partner variable.

The store keeps the most recent 200 messages per conversation.

This store is local persistence only. It is not the authoritative source of remote message data.

## Outbox

`ChatOutboxStore` is another `SharedPreferences`-backed store named `sigma_bridge_chat_outbox`.

It persists messages that have not yet been delivered to Supabase. Loading the outbox treats stored items as `PENDING` so retries can continue after process restart.

The background chat service can retry pending messages across multiple conversations rather than only the currently open conversation.

## Conversation list

`ChatConversationStore` maintains the local conversation list and preview data. It is separate from message history so the UI can render the chat list quickly.

A conversation contains, at minimum, the partner ID, display name, latest message preview, latest-message timestamp, and optional avatar path. Up to 100 conversations are kept and sorted by recent activity.

## Profiles and presence

`ChatProfileRepository` uses RPCs for profile operations. The current operations include:

```text
sigma_get_my_profile
sigma_get_profile_by_public_id
sigma_get_last_seen
sigma_touch_last_seen
sigma_update_profile
sigma_search_users
sigma_update_avatar
```

Avatar files are stored in the `chat_avatars` storage bucket. The current client accepts JPEG/JPG/PNG/WebP and limits uploads to 5 MB. Avatar updates use a fresh object path rather than overwriting an existing object.

Presence is implemented using a last-seen timestamp. `ChatViewModel` periodically touches the user's own last-seen value and fetches the partner's last-seen value. The UI considers the partner online when the last-seen timestamp falls inside the configured online window.

## User discovery and first contact

`ChatInboxRepository` can fetch undelivered messages independently of the locally selected partner. This allows a user to receive a first message without first searching for or opening the sender's conversation.

The background notification service derives the correct partner-specific history/encryption context from the sender identifier for these messages.

## Background notification service

`ChatNotificationService` is the Private Chat background service. Its responsibilities include:

- registering the identity/device
- observing the undelivered inbox
- observing conversation messages in the background
- adding unread messages
- sending Delivered receipts
- retrying pending outgoing messages
- processing remote translation jobs
- publishing notifications for conversations that are not open

It returns `START_STICKY` and is started for authenticated Private Chat use. `ChatBootReceiver` can start it after boot for authenticated users.

The service uses `ChatForegroundState.openPartnerId` to avoid issuing unread notifications for the conversation currently visible to the user.

## Translation architecture

Private Chat translation supports two execution paths conceptually:

### Local/primary translation

`ChatGeminiTranslationRepository` sends translation requests to Gemini using the app's configured Private Chat Gemini keys.

### Primary/secondary relay

`ChatTranslationRelayRepository` coordinates remote translation jobs through Supabase RPCs. A client can request a translation by `client_message_id` and target language; a worker can claim jobs, complete them with encrypted translation ciphertext, or mark them failed.

The relay stores encrypted translated text. It does not require Telegram.

## Current UX contract

The Private Chat UX should preserve these guarantees:

1. A received message appears before translation completes.
2. Original text is never discarded as a consequence of translation.
3. Read receipts do not wait for translation.
4. Sending a message creates local state before network delivery.
5. Failed delivery remains retryable through the outbox.
6. Conversation data is keyed per partner/conversation.
7. Background processing must not depend on the chat that happens to be open in the UI.
